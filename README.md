# supplier-sync

여러 외부 숙박 공급사(supplier)의 서로 다른 API를 하나의 표준 숙박 상품 모델로 통합하는 연동 백엔드입니다.
공급사마다 요금을 표현하는 방식(날짜별 단가 vs 기간 총액), 세금 처리(별도 vs 포함), 실패를 알리는
방식(HTTP 상태 코드 vs 항상 200 + 본문 코드)이 제각각이지만, 고객은 상품이 어느 공급사에서 왔는지와
무관하게 언제나 동일한 형태의 검색 결과를 받습니다.

## 기술 스택

| 영역 | 선택 |
|---|---|
| 언어 · 프레임워크 | Kotlin, Spring Boot 3.4.13 |
| 런타임 | JDK 21 (Gradle toolchain 고정) |
| 웹 모델 | Spring MVC + WebClient — 논블로킹은 외부 병렬 호출 구간에만 |
| 영속화 | Spring Data JPA + MySQL 8.4 (LTS) — 테스트도 동일 엔진·동일 버전 |
| 회복탄력성 | Resilience4j (재시도·서킷 도입 시) |
| 지표 | Micrometer + Prometheus 노출 |

각 선택의 근거와 택하지 않은 대안은 [docs/TECH_STACK.md](docs/TECH_STACK.md)에 있습니다.

## 빌드와 실행

```bash
docker compose up -d --wait  # 로컬 MySQL 8.4 기동, 준비 완료까지 대기 — 데이터는 네임드 볼륨에 유지
./gradlew build              # 컴파일 + 테스트
./gradlew test               # 테스트만 실행
./gradlew bootRun            # 애플리케이션 실행 (기본 8080)
```

JDK 21이 필요합니다. Gradle toolchain이 컴파일 대상을, `gradle/gradle-daemon-jvm.properties`가 빌드를
수행하는 데몬 JVM을 각각 21로 고정하므로, 셸의 기본 java가 다른 버전이어도 `./gradlew`는 그대로
동작합니다. Docker도 필요합니다 — 실행은 compose의 MySQL을 쓰고, 테스트는 Testcontainers가 스스로 띄우는
MySQL을 씁니다(compose 기동 여부와 무관). Docker 데몬(Engine)은 **25 이상**이어야 합니다 —
Testcontainers의 도커 클라이언트가 요구하는 API 1.44가 Engine 25.0부터 제공되며, 그보다 오래된 데몬에서는
`client version 1.44 is too new` 오류로 테스트 컨테이너 기동이 실패합니다.

> 현재 저장소는 설계 라운드를 마치고 구현을 단계적으로 진행하는 중입니다. 설계 결정은 전부 문서화되어
> 있으며, 구현은 브랜치와 PR 단위로 쌓아 과정이 커밋 히스토리에 드러나게 합니다. 진행 상황과 의사결정
> 과정은 [JOURNAL.md](JOURNAL.md)를 참고하세요.

## 핵심 설계 요약

**통합 모델은 교집합만 담습니다.** 공급사들이 공통으로 채울 수 있는 정보만 표준으로 삼습니다 — 한쪽만 주는
정보를 nullable로 들이면 소비자가 결국 공급사별 분기를 하게 되고, 공급사가 늘수록 고유 필드의 합집합은
발산하기 때문입니다. 필요가 생기면 공통 모델을 명시적으로 변경하며, 현재 예외는 하나(일자별 실측 요금)뿐
입니다. → [docs/DOMAIN_MODEL.md](docs/DOMAIN_MODEL.md)

**요금은 세금 포함 총액이 기준입니다.** 두 공급사가 공통으로 도달할 수 있는 지점은 총액뿐이고, 고객에게도
"전체 내가 내는 금액"이 가장 정직한 숫자입니다. 여기에 평균 1박가(총액÷박수, 내림)를 항상 제공하고, 일자별
실측 금액은 주는 공급사에 한해 포함합니다.

**내부 식별자는 대리키입니다.** 공급사 식별자는 유일성 범위가 제각각이라, BIGINT 자동 증가 대리키에 자연키
UNIQUE 제약을 걸어 "같은 공급사 상품은 언제나 같은 내부 id"를 DB 수준에서 보장합니다. 저장하는 것은 이
매핑뿐이며, 요금·재고는 저장하지 않습니다. → [docs/ERD.md](docs/ERD.md)

**가용성은 3상태로 판정합니다.** 연박 예약 가능 수는 날짜별 잔여의 최소값(병목)이고, 데이터가 누락된 날은
재고 0으로 간주합니다 — 오버부킹(고객 피해)과 기회 손실(우리 손해)의 비대칭 때문에 "확실하지 않으면 팔지
않습니다". 확정 매진은 매진 표시로 노출하고(취소 알림 등 후속 기능의 진입점), 미확정만 응답에서 제외합니다.

**실패는 어댑터에서 통일됩니다.** HTTP 상태로 실패를 알리는 공급사와 항상 200에 본문 코드로 알리는
공급사를 어댑터가 공통 예외 하나로 수렴시키고, 재시도 가능 여부도 그 자리에서 분류합니다. 부분 실패는 정상
흐름입니다 — 성공한 공급사의 결과로 응답하고 실패 사실은 응답의 `errors`로 드러냅니다.
→ [docs/INTEGRATION.md](docs/INTEGRATION.md)

**아키텍처는 두 단계 변환의 경계가 중심입니다.** 어댑터는 공급사 원시 형식을 통일된 중간 타입으로만
바꾸고(내부 id를 모르는 것이 경계의 핵심), 정규화가 매핑·판정을 거쳐 표준 모델을 만듭니다. 신규 공급사
추가는 어댑터 하나로 끝나야 하며, 기존 계층을 고쳐야 한다면 경계가 샌 것입니다.
→ [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)

## API

```
GET /api/v1/stays/search?checkIn=2026-09-01&checkOut=2026-09-04&adults=2&children=0
```

날짜와 인원으로 보유 숙소 전체를 여러 공급사에 병렬 조회하고, 정규화·병합한 `stayProducts`와 공급사별 실패
정보 `errors`를 반환합니다. 계약 상세(검증 규칙, 응답 구조, 오류 포맷)는
[docs/API.md](docs/API.md)에 있습니다.
