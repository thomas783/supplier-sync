# 기술 스택

스택 하나하나가 "왜 이것인가"에 답할 수 있어야 한다는 원칙으로 골랐습니다. 아래는 확정된 기반 스택과 각
선택의 근거, 검토했다가 택하지 않은 대안입니다. 아직 결정하지 않은 영역은 문서 끝에 명시해 두었습니다 —
문서와 결정이 코드보다 앞서 나가지 않게 하기 위해서입니다. 결정 과정의 상세한 흐름은 `JOURNAL.md`에
있습니다.

## 한눈에 보기

| 영역 | 선택 | 버전 |
|---|---|---|
| 언어 | Kotlin | 2.1.20 |
| 프레임워크 | Spring Boot | 3.4.13 |
| 런타임 | JDK (Temurin) | 21 |
| 빌드 | Gradle (Kotlin DSL) + Wrapper | 8.10.2 |
| 웹 | Spring MVC (Tomcat) | Boot 관리 |
| HTTP 클라이언트 | Spring WebClient (Reactor Netty) | Boot 관리 |
| 영속화 | Spring Data JPA + MySQL | MySQL 8.4 (LTS) |
| 회복탄력성 | Resilience4j (retry + circuit breaker) | 2.2.0 (BOM 밖 명시 고정) |

## 선택의 근거

### Spring Boot 3.4.13 — 위험의 비대칭성

3.4 계열의 최신 안정 패치로 고정했습니다. 최신 메이저(4.x)와 비교했을 때 판단 기준은 위험의
비대칭성이었습니다. 4.x가 주는 실익(프레임워크 수준 API 버저닝, JSpecify 널 안전성 등)은 이 프로젝트
범위에 거의 영향이 없는 반면, 감수해야 할 위험 — 외부 연동·회복탄력성 계열 부가 라이브러리의 호환 문제,
막혔을 때 참고 자료 부족 — 은 곧바로 일정을 잡아먹습니다. 외부 연동이 핵심인 프로젝트라 부가 라이브러리
생태계의 검증 여부를 특히 무겁게 봤습니다. 실제로 Spring Initializr가 4.x BOM 해석이 깨져 있는 것을 직접
겪어, 초기 난기류의 방증으로 삼았습니다(그래서 빌드 스크립트도 Initializr 없이 직접 관리합니다).

3.5.x도 검토했으나, 지원 기간의 이점만 있고 프로그래밍 모델이 3.4와 사실상 동일해 채택하지 않았습니다.
이 프로젝트의 우선순위는 최신성·지원 기간보다 완성도와 리뷰 환경의 재현성입니다.

### JDK 21 — 조합의 정합성

요구 하한(Java 21+)을 만족하는 실질 후보는 LTS인 21과 25였습니다. 21을 택한 결정적 이유는 조합의
정합성입니다. Boot 3.4.13 + Kotlin 2.1.20 + Gradle 8.10.2는 전부 JDK 21을 중심으로 검증된 묶음이고, 25로
올리는 순간 Kotlin과 Gradle까지 연쇄로 올려야 하는데 그 대가로 얻는 것이 Kotlin 코드베이스에서는 사실상
없습니다 — Java의 신규 언어 기능은 Kotlin 사용자에게 무의미하고, 런타임 개선은 이 규모에서 체감되지
않습니다. 실제로 Gradle을 Java 25로 실행했을 때 Kotlin 컴파일러가 버전 문자열을 파싱하지 못해 빌드가
깨지는 것을 겪었습니다.

주의할 점: toolchain은 "컴파일 대상"만 고정할 뿐 Gradle 자체를 실행하는 JVM은 별개입니다. 셸의
`JAVA_HOME`도 21을 가리키게 하는 것이 안전합니다.

### Gradle (Kotlin DSL) + Wrapper

빌드 스크립트를 Kotlin DSL로 작성하고 Wrapper(8.10.2)를 커밋해, 리뷰 환경에서 별도 Gradle 설치 없이
동일한 버전으로 빌드되게 합니다.

### MVC + WebClient — 논블로킹은 가치를 내는 구간에만

이 시스템의 웹 표면은 검색 엔드포인트 수준으로 단순하고, 난점은 바깥으로 나가는 병렬 호출에 있으며,
영속화는 JPA(블로킹)를 씁니다. 필요한 능력 — 다수 공급사 병렬 호출, 호출별 타임아웃, 부분 실패 조합 — 은
WebClient가 제공하는 것이지 WebFlux 서버 모델이 제공하는 것이 아닙니다. 그래서 웹 계층은 MVC(Tomcat)로
단순하게 두고, 외부 연동 구간에만 WebClient의 논블로킹 조합을 쓰며, 컨트롤러 경계에서 `.block()`으로 값을
모읍니다.

WebFlux 전면 도입은 JPA 블로킹 경계 처리(별도 스케줄러 또는 R2DBC 전환)라는 구체적 비용을 얹는 대신 우리
규모에서 체감되지 않는 처리량 여유만 주기 때문에 택하지 않았습니다. 초고동시성과 수 초짜리 외부 응답으로
요청 스레드 고갈이 실제 문제가 되는 환경이라면 재검토할 수 있습니다.

### MySQL 8.4 — 영속성, 그리고 테스트도 같은 엔진·같은 버전으로

런타임 DB는 MySQL 8.4(LTS)로 고정합니다. 영속성이 필요하다는 판단과 함께, 인메모리 DB(H2)로 테스트하면
SQL 방언(dialect)과 제약 동작이 실DB와 달라질 수 있다는 점을 처음부터 제거하기 위해 **테스트도 운영과
동일한 MySQL 버전을 구동해 실행**하는 것을 원칙으로 삼았습니다. 도커 이미지와 테스트에서 구동하는
컨테이너 모두 `mysql:8.4`로 통일합니다.

버전은 8.4를 택했습니다 — 8.0은 지원이 종료되어 신규 고정 대상으로 부적절하고, 9.x는 이노베이션 릴리스라
서버 고정 대상이 아닙니다.

구동 방식은 역할별로 분리합니다. **로컬 개발은 docker compose**로 띄우고 데이터를 네임드 볼륨에
유지합니다(초기화는 `docker compose down -v`로만, 명시적으로). **테스트는 Testcontainers**가 실행 시점에
컨테이너를 스스로 띄우고 정리합니다 — 테스트가 외부 상태(컨테이너가 떠 있는지, 이전 실행의 잔여 데이터)에
의존하지 않아 로컬과 CI에서 같은 방식으로 재현됩니다.

스키마는 별도 마이그레이션 도구 없이 **Hibernate `ddl-auto`가 엔티티 정의에서 생성**합니다(로컬
`update`, 테스트 `create`). Flyway도 검토했으나 테이블 두 개 규모에는 마이그레이션 파일 관리가 얻는
것보다 큰 과잉이라 보류했습니다 — 스키마 변경 이력이 실제로 쌓이기 시작하면 재검토합니다.

### MockWebServer — 어댑터 HTTP 검증

공급사 어댑터 테스트는 로컬 목 HTTP 서버(MockWebServer)로 실제 HTTP 계층을 통과해 검증합니다 —
직렬화, 상태 코드 해석, 무응답 타임아웃은 HTTP 를 실제로 오가야 검증되는 동작이라 메서드 수준
모킹으로는 대체되지 않습니다. 의존성이 가볍고 응답 큐잉·요청 검증이 단순하며, 버전은 Boot BOM 관리
밖이라 명시적으로 고정합니다.

### Resilience4j — 호출 지점과의 궁합

외부 호출이 WebClient의 Reactor 체인(Mono/Flux) 안에서 일어나므로, 실패 처리 도구도 그 체인에 자연스럽게
결합해야 합니다. 필요한 능력 세 가지 — 일시적 실패만 골라 하는 재시도, 반복 실패하는 공급사를 끊는 공급사별
서킷 브레이커, 동작이 보이게 하는 지표 연동 — 를 기준으로 비교했을 때, Resilience4j는 셋을 전부 충족하는
유일한 성숙 선택지였습니다. Mono 체인에 그대로 끼워 넣는 전용 연산자를 제공하고, 설정을 yml로 외부화할 수
있으며, Micrometer 지표가 자동 등록됩니다. 버전은 BOM 관리 밖이므로 명시적으로 고정합니다(2.2.0).

Spring Retry는 블로킹 메서드 대상 AOP라 리액티브 구간에 맞지 않아 배제했고, Reactor 내장 `retryWhen`
최소주의(서킷은 나중에)는 공급사 장애가 일상인 도메인 특성상 서킷의 가치가 분명하고 나중에 도입하면 재시도
코드까지 갈아엎게 되는 경로라 거부했습니다. Spring Framework 7의 코어 재시도 어노테이션은 Boot 4
전용이라 3.4 선택과 일관되게 해당 없습니다.

## 검토했다가 택하지 않은 것

- **Spring Boot 4.x** — 릴리스 초기의 생태계·재현성 리스크 대비 실익 없음.
- **Spring Boot 3.5.x** — 지원 기간 이점뿐, 프로그래밍 모델 동일.
- **JDK 25** — Kotlin·Gradle 연쇄 업그레이드 비용 대비 Kotlin 코드베이스에서 체감 이득 없음.
- **WebFlux 전면 도입** — JPA 블로킹 경계 비용 대비 이 규모에서 이점 없음.
- **H2 (런타임)** — 영속성 판단과 dialect 불일치 제거를 위해 거부. 테스트조차 실DB와 동일 버전으로 간다.
- **Spring Retry** — 리액티브 체인과 결합 불가.
- **Reactor 내장 retry 최소주의** — 서킷 브레이커 부재, 도입 시점만 미루는 경로.
- **Flyway** — 테이블 두 개 규모에 과잉. 스키마 변경 이력이 쌓이기 시작하면 재검토.

## 아직 결정하지 않은 것 (해당 기능 논의 때 확정)

- **지표 수집** — Micrometer + Prometheus 노출 여부와 계측 설계는 관측성 작업 때.
- **API 문서화** — SpringDoc/Swagger 도입 여부는 웹 API 작업 때.
