# 중복 상품 병합 — 카탈로그 그룹핑 (설계 — 추후)

이 문서는 서로 다른 공급사가 파는 **같은 물리 숙소**를 하나로 묶어 보여주는 설계만 담습니다. 구현하지
않으며, 그때까지의 동작은 식별자 전략의 귀결로 공급사가 다르면 별개 상품으로 나란히 노출됩니다
([DOMAIN_MODEL.md](DOMAIN_MODEL.md)).

## 문제 — 같은 숙소인데 공통 키가 없다

공급사 A 의 `A-10023` 과 공급사 B 의 `B77120` 이 실제로 같은 호텔이어도, 그걸 알려주는 공통 식별자가
스펙에 없습니다. 지금은 둘이 별개 내부 id 를 받아 검색 결과에 따로 뜹니다 — 고객은 같은 호텔을 두 줄로
보게 되고, "어느 공급사가 더 싼가"를 스스로 비교해야 합니다.

## 목표 형태 — 그룹핑(메타서치 스타일), 병합 아님

물리 숙소를 **한 번만** 노출하고, 그 아래에 공급사별 오퍼(옵션·가격)를 묶어 보여줍니다 — hotels.com·
Google Hotels 같은 메타서치의 카드 형태입니다.

```
🏨 Riverside Hotel Seoul            ← 물리 숙소 1개(카탈로그 엔티티)
   ├─ 공급사 A · 디럭스 트윈 · 조식 포함 · 429,000원
   ├─ 공급사 A · 디럭스 트윈 · 조식 미포함 · 399,000원   ← 같은 방도 요율(프로모션·조식)로 오퍼가 갈림
   └─ 공급사 B · 디럭스 트윈 · 조식 포함 · 452,000원
```

- **병합이 아니라 그룹핑인 이유**: 같은 방이라도 공급사·프로모션·조식 포함 여부에 따라 요금이 다릅니다.
  하나의 가격으로 접으면 그 다양성(과 "어디가 싼가"의 비교 가치)이 사라집니다. 그래서 숙소는 하나로
  묶되, **오퍼는 공급사 × 옵션 × 가격 단위로 나란히** 둡니다.
- **오퍼의 단위**: 공급사 × 객실 타입 × 요율(조식·프로모션 등) = 오퍼 하나. 지금의 `StayProduct` 하나가
  곧 오퍼 하나가 되고, 그것들을 카탈로그 숙소로 그룹핑하는 층이 위에 얹힙니다.

## 카탈로그 테이블 — 그룹핑 키를 사전 보관

공급사 코드 위에 **정규 숙소(canonical property)** 를 두는 테이블을 만들고, 공급사 매핑을 거기에
링크합니다. 기존 `property` 매핑([ERD.md](ERD.md))의 상위 그룹핑 키입니다.

```
catalog_property                     property (기존 매핑)
  id            PK                      id                PK
  canonical_name                        supplier          (A|B)
  (좌표·주소 등 메타)                    supplier_property_code
                                        catalog_property_id  FK → catalog_property.id  (nullable)
```

- **링크는 nullable**: 카탈로그에 아직 매칭이 없는 공급사 숙소는 `catalog_property_id = null` 로 남아
  **단독 노출**(현 동작)됩니다. 병합은 **가산적**입니다 — 매핑된 숙소만 그룹지고, 나머지는 그대로. 이
  덕분에 카탈로그가 비어 있어도 시스템이 정상 동작하고, 커버리지를 점진적으로 늘릴 수 있습니다.
- **사전 보관인 이유**: 매칭은 비싸고(아래) 검색 핫패스에서 매번 하기 어렵습니다. 카탈로그로 결과를
  미리 굳혀 두면, 검색은 그룹핑 키를 조회만 하면 됩니다.

## 매칭을 어떻게 채우나 — 정밀도 우선

카탈로그의 링크(어느 공급사 코드가 같은 숙소인가)를 채우는 것이 이 설계의 진짜 난제입니다.

| 방식 | 성격 | 한계 |
|---|---|---|
| **큐레이션**(권장 기본) | 운영자가 매핑을 검토·확정 | 정밀하지만 손이 들고 규모 한계 |
| **자동 매칭**(보조) | 이름·좌표·주소의 퍼지 매칭으로 후보 제시 | 규모는 되지만 **오탐 위험** — 검토 없이 자동 확정은 금물 |

- **오탐이 치명적입니다**: 서로 다른 두 호텔을 같은 것으로 묶으면 **고객이 엉뚱한 숙소를 예약**하는
  사고입니다(재고를 잘못 파는 것과 같은 층위 —[DOMAIN_MODEL.md](DOMAIN_MODEL.md)의 보수 원칙). 그래서
  **재현율보다 정밀도**를 택합니다 — 자동 매칭은 "후보 제시"까지만 하고, 확정은 큐레이션(또는 높은
  신뢰도 임계 + 사후 검토)이 담당합니다. 확신이 없으면 묶지 않고 단독 노출하는 편이 안전합니다.
- **신뢰도 관리**: 링크마다 출처(수동·자동)와 신뢰도를 남겨, 오탐이 발견되면 그 링크만 끊어 단독 노출로
  되돌릴 수 있게 합니다.

## 그룹핑 단위 — 숙소 레벨만(초기)

- **숙소 레벨 그룹핑**만 먼저 합니다. 객실 레벨 병합(공급사 A 의 "Deluxe Twin" = 공급사 B 의 "Deluxe
  Twin Room" 인가)은 숙소 매칭보다 더 어렵고 오탐 여지가 크므로 **보류**합니다 — 초기에는 한 숙소 그룹
  안에서 객실·오퍼가 공급사별로 나란히 놓일 뿐, 객실을 가로질러 합치지 않습니다.
- 객실 레벨 병합은 숙소 카탈로그가 안정된 뒤 별도로 논의합니다.

## 응답 계약 변경 — v2 후보

현재 응답은 `stayProducts` 의 **플랫 리스트**입니다([API.md](API.md)). 그룹핑은 이를 **숙소 → 오퍼 목록**의
중첩 구조로 바꾸므로, 기존 소비자를 깨뜨립니다. 따라서 병합은 **응답 계약의 새 버전(`/api/v2`)** 으로
도입하는 것을 원칙으로 합니다(페이징·정렬 재론과 같은 계열의 계약 변경 —[DESIGN_DECISIONS.md](DESIGN_DECISIONS.md)).
그룹 내 정렬(예: 최저가 오퍼 우선)과 그룹 간 정렬도 이때 정의합니다.

## 미결 — 구현 시 결정

- **매칭 소스·임계**: 자동 매칭의 신호(이름·좌표·주소·전화)와 확정 신뢰도 임계, 큐레이션 워크플로.
- **객실 레벨 병합**: 숙소 그룹이 안정된 뒤 별도로 논의.
- **정렬·중복 오퍼**: 그룹 내/간 정렬 기준, 같은 공급사가 사실상 동일한 오퍼를 중복으로 줄 때의 처리.
- **카탈로그 채움 경로**: 숙소 목록 동기화([ARCHITECTURE.md](ARCHITECTURE.md))와 어떻게 연동해
  카탈로그를 최신으로 유지할지.
