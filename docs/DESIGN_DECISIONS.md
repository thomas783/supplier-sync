# 보류된 설계 결정 모음

지금 구현하지 않기로 한 것들의 목록입니다. "하지 않은 것"에도 이유가 있어야 한다는 원칙에 따라, 각 항목에
보류의 근거와 — 논의가 이미 진행된 경우 — 도입 시점의 출발점이 될 초안을 함께 남깁니다. 결정 과정의 상세한
흐름은 `JOURNAL.md`에 있습니다.

## 재시도 정책 — 추후 구현

선택 구현 영역이므로 필수 견고성(병렬 호출·타임아웃·부분 실패·실패 판정 통일)을 먼저 완성한 뒤 도입합니다.
토대는 이미 깔려 있습니다 — 어댑터가 실패에 재시도 가능 여부(retryable)를 분류해 두므로, 정책은 공급사를
몰라도 "retryable이면 재시도" 한 줄이 됩니다.

도입 시점의 정책 초안: 즉답형 일시 오류(5xx·429·`E500`/`E503`/`E429`)만 재시도 1회, 고정 200ms 간격.
**타임아웃은 재시도 제외** — 실패 확인에 이미 5초를 쓴 뒤 또 5초를 거는 것은 성공 확률 대비 비용이 나쁘고,
무응답 공급사가 검색을 5초 × 시도 횟수로 묶게 됩니다. 조회(GET)의 멱등성이 전제이며, 쓰기(예약)에는 별도
정책이 필요합니다. 상세는 [INTEGRATION.md](INTEGRATION.md)를 참고하세요.

## 서킷 브레이커 — 추후 구현

같은 이유로 보류합니다. 도입 시점의 방향: 공급사별로 분리해 반복 실패를 빠르게 차단 — 의도적으로 관대하게
잡은 응답 타임아웃(5초)의 반복 비용을 끊는 역할입니다. 도구는 스택 결정대로 Resilience4j를 씁니다
([TECH_STACK.md](TECH_STACK.md)). 도입 시 관측 지표에 `circuit_open` outcome과 서킷 상태 알람을
추가합니다([MONITORING.md](MONITORING.md)).

## 요금·재고 캐시 전략과 숙소 수천 개 대응 — 묶어서 재논의

숙소가 수천 개로 늘면 "검색 시 전량 실시간 조회" 구조는 지연이 N에 선형이라 유지가 어렵습니다 — 청크 수 =
공급사 수 × ⌈N/50⌉이고, 동시성 상한은 폭주를 막을 뿐 지연을 줄이지 못한다는 분석을 마쳤습니다. 검토된
수단(짧은 TTL 캐시, 백그라운드 사전 수집·스냅샷, 대상 축소, 점진 응답)과 단계 로드맵 초안은
[INTEGRATION.md](INTEGRATION.md)에 있습니다.

**캐싱이 핵심 수단이 될 사안이라 캐시 전략 논의와 묶어 재논의합니다.** 그 논의의 축은 — 짧은 TTL과 정합성
오차 허용 범위(스테일 캐시는 곧 오버부킹이라 "엄격 판정" 원칙과 긴장 관계), 스냅샷 전환 시 "요금·재고
저장 안 함" 원칙의 명시적 변경, 전환 트리거(검색 p95 초과, 429 관측)입니다.

## 중복 상품 병합 — 추후 논의

두 공급사가 실제로 같은 숙소를 팔아도 이를 알려주는 공통 키가 없습니다. 그때까지의 동작은 식별자 전략의
귀결로, 공급사가 다르면 별개 상품으로 나란히 노출됩니다. 병합을 논의할 때의 선결 조건은 추정 매칭의 신뢰도
관리(오탐은 서로 다른 숙소를 하나로 합쳐 파는 사고)와 공급사 간 조건 차이(총액·조식)의 표현 방식입니다.
상세는 [DOMAIN_MODEL.md](DOMAIN_MODEL.md)의 미결 목록을 참고하세요.

## 환율·다중 통화 처리 — 추후 논의

현재 범위는 KRW뿐입니다. 통화 코드가 모델에 보존되므로 데이터 유실은 없지만, 서로 다른 통화의 상품을 함께
노출·비교하려면 환율이 필요합니다. 그 시점에 묶어 결정할 것들 — 금액 타입의 `BigDecimal` 전환과 반올림
정책, 환율 소스와 기준 시점, 환산가와 원통화가의 표시 방식. 상세는
[DOMAIN_MODEL.md](DOMAIN_MODEL.md)의 미결 목록을 참고하세요.
