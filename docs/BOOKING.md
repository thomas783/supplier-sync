# 예약 대행 흐름 (설계 — 예약 기능 도입 시)

이 문서는 고객 대신 공급사에 예약을 생성·취소하는 **예약 대행**의 흐름 설계만 담습니다. 현재 시스템은
검색 전용이라 구현하지 않으며, 예약 기능이 범위에 들어오는 시점에 이 설계대로 도입합니다. 진실의 원천은
언제나 공급사이고, 우리는 그 예약을 중개·기록할 뿐입니다.

## 흐름 — 검색 스냅샷에서 확정까지

검색 결과는 조회 시점의 스냅샷(캐시 tolerant)이고, 예약은 정확해야 하는 커밋입니다. 그 간극을 예약 시점
재검증이 메웁니다.

```
오퍼 선택(검색 스냅샷: 공급사·숙소·객실·요율·가격)
  → ① 예약 시점 재검증 — 공급사에 현재 가격·재고 실시간 확인
       ├─ 그대로   → 계속
       └─ 변동·매진 → 고객에게 고지(가격 변동/판매 종료), 진행 중단
  → ② 예약 생성 — 공급사에 예약 요청(멱등키 첨부) → 공급사 예약 id 수신
  → ③ 기록 — 우리 예약 레코드 저장(우리 id ↔ 공급사 예약 id, 상태, 멱등키)
  → ④ 캐시 갱신 — 해당 숙소 키 무효화(재고 감소 반영)

취소:
  → 공급사에 취소 요청 → 상태 갱신 → 해당 숙소 키 무효화(재고 복원 반영)
```

## ① 예약 시점 재검증 — 여러 문서가 참조하던 "최종 방어선"의 실현

검색 캐시는 최대 hard TTL 만큼 낡을 수 있고([CACHING.md](CACHING.md)), 가용성 판정도 조회 시점 스냅샷일
뿐입니다. **오버부킹을 막는 최종 방어선은 여기 — 예약 직전 공급사 실시간 재조회** 입니다. 그래서 검색이
관대해도(캐시 stale, 표시 품질 예산) 안전한 것이고, 이 재검증이 그 관대함을 떠받칩니다.

- 재검증에서 **가격이 변했으면** 고객에게 새 가격을 고지하고 동의를 받습니다(메타서치의 "가격이
  변경되었습니다" — Google Hotel 의 캐시가·최종가 일치 전제와 같은 구조).
- **매진이면** 판매 종료로 처리합니다 — 검색에서 "가능"으로 보였더라도 여기서 걸립니다.

## ② 멱등성과 불명확한 결과 — 돈이 걸린 연산의 규율

예약은 검색과 다릅니다 — 부분 실패가 정상 흐름인 검색과 달리, 예약은 **중복 생성이 곧 사고**(이중 예약)인
비가역 연산입니다.

- **멱등키**: 예약 요청마다 고유 키를 붙여, 재시도가 새 예약을 만들지 않게 합니다(공급사가 멱등키를
  지원하면 그대로, 아니면 우리 쪽 중복 방지로 보강).
- **불명확한 결과**: 예약 요청이 타임아웃되면 **공급사가 만들었는지 안 만들었는지 모릅니다.** 검색처럼
  "재시도 제외"로 끝낼 수 없습니다 — 멱등키로 **공급사에 조회(reconciliation)** 해 실제 상태를 확인하고
  우리 레코드를 맞춥니다. 확인 전까지는 미확정 상태로 잠급니다.

## ③ 실패 시 보상 처리 — 사가 롤백

예약은 우리 레코드·공급사·(결제)에 걸친 여러 단계인데, **공급사 예약 생성은 외부 부수효과라 DB
트랜잭션으로 되돌릴 수 없습니다.** 그래서 앞 단계가 성립한 뒤 뒷 단계가 실패하면, 성립한 외부 단계를
**보상 동작으로 되돌립니다**(사가 패턴). 전진 단계와 그 보상은 짝을 이룹니다.

| 전진 단계 | 보상 동작 |
|---|---|
| 공급사 예약 생성 | 공급사 예약 취소 |
| (결제 — 범위 밖) | 환불 |

- **트리거**: "공급사 예약 생성"이 **성공한 걸 아는데** 그 뒤 단계(레코드 저장, 결제)가 실패하면 보상을
  실행합니다. 이것이 조정(reconciliation)과 다른 점입니다 — 조정은 *성공 여부가 불확실한* 상태의
  해소이고, 보상은 *확실히 성립한* 단계의 되돌림입니다.
- **보상도 외부 호출이라 실패할 수 있습니다**: 즉시 1회로 끝내지 않고, 실패 시 재시도 큐·배치로
  "성립했지만 완결하지 못한 예약"을 쓸어 담습니다 — 그냥 두면 유령 예약(고객은 취소된 줄 아는데 공급사엔
  살아 있는)이 남습니다. 보상 취소는 멱등해야 합니다(두 번 취소해도 안전).
- **캐시와 이어집니다**: 보상 취소가 성립하면 재고가 복원되므로, ④의 이벤트 무효화로 그 숙소 키를 지워
  검색에 다시 뜨게 합니다.

## ④ 캐시 갱신 — 생성·취소 이벤트로 해당 숙소 무효화

예약 성공은 그 숙소의 **재고를 줄이고**, 취소는 **되돌립니다.** 이 변화를 검색 캐시에 즉시 반영하지 않으면,
방금 마지막 방을 예약했는데 검색에는 아직 "가능"으로 남는 괴리가 생깁니다. 그래서 **예약 생성·취소를
이벤트로 삼아 해당 숙소의 캐시 키를 무효화**합니다.

- **무효화(재fetch)이지 낙관적 감산이 아닙니다**: 진실의 원천은 공급사입니다. 우리가 캐시 값을 직접
  깎으면(예: 잔여 −1) 공급사의 실제 상태와 어긋날 수 있습니다(다른 채널의 예약·취소, 오버부킹 정책 등).
  키를 무효화해 **다음 검색이 공급사에서 새로 가져오게** 하는 편이 단일 원천 원칙에 맞습니다.
- **범위는 그 숙소만**: 캐시 키가 숙소 단위라([CACHING.md](CACHING.md)), 예약된 숙소의 키만 지우면
  됩니다 — 무고한 다른 숙소의 캐시는 보존됩니다. (요청 단위 축약형이었다면 값에 여러 숙소가 섞여 태그
  기반 선별 삭제가 필요합니다.) 이것이 CACHING.md 가 "예약 흐름 도입 시 추가"로 미뤄 둔 이벤트 무효화의
  실현입니다.
- **비차단**: 캐시 무효화 실패가 예약 자체를 되돌리면 안 됩니다 — 예약은 이미 공급사에 성립했으므로,
  무효화는 best-effort 로 하고 실패는 로그·재시도로 흡수합니다(TTL 이 결국 자연 만료로 정합성을 회복).

## 영속 — 예약 레코드

예약은 검색과 달리 **상태를 저장**합니다(검색은 비영속). 최소한:

| 필드 | 내용 |
|---|---|
| 내부 예약 id | 우리 대리키 |
| 공급사 · 공급사 예약 id | 취소·조회의 열쇠 |
| 숙소·객실·기간·인원 | 재현·무효화 범위 |
| 확정 금액·통화 | 재검증에서 확정된 값([CURRENCY.md](CURRENCY.md)의 원가·환산가) |
| 멱등키 | 중복 방지·조정의 열쇠 |
| 상태 | 미확정 → 확정 → (취소) 상태 기계 |

## 경계와 미결

- **결제 주체**: 결제를 우리가 대행하는지, 공급사로 넘기는지는 예약 기능의 상위 결정입니다 — 이 문서는
  재고·상태 흐름만 다루고, 결제·PG 연동은 범위 밖으로 둡니다.
- **취소 정책·환불**: 공급사별 취소 규정(무료 취소 기한 등)의 표현·전달.
- **상태 기계의 완전성**: 부분 취소, 노쇼, 공급사 측 취소(초과예약 등)까지의 상태 확장.
- **재검증과 예약의 원자성**: ①과 ② 사이에 재고가 또 바뀔 수 있으므로, 공급사가 "가격 보장 토큰"이나
  hold(임시 점유)를 제공하면 그것을 활용할지.
