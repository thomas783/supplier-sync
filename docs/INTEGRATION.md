# 공급사 연동

외부 연동은 언제든 실패할 수 있다는 전제로 설계합니다. 이 문서는 공급사 간 스펙 차이를 어떻게 흡수하는지,
실패에 어떻게 대비하는지, 그리고 신규 공급사를 어떻게 추가하는지를 다룹니다. 결정 과정의 상세한 흐름은
`JOURNAL.md`에 있습니다.

## 두 공급사의 차이와 흡수 방식

| 축 | 공급사 A | 공급사 B | 흡수 방식 |
|---|---|---|---|
| 요금 | 날짜별 1박 단가, 세금 별도 | 기간 전체 총액, 세금 포함 | 어댑터가 세금 포함 총액(gross)으로 통일 — A는 합산, B는 그대로 |
| 실패 전달 | HTTP 4xx/5xx | **항상 HTTP 200** + 본문 `resultCode` | 어댑터가 공통 예외 하나로 통일 (아래) |
| 식별자 | hotelCode / roomTypeCode | propertyId / roomId | 내부 대리키로 매핑 ([ERD.md](ERD.md)) |
| 재고 | 날짜별 잔여 객실 수 | 날짜별 잔여 객실 수 | 공통 — 날짜별 잔여로 정규화 |

조회는 성격이 다른 두 단계로 나뉩니다. **숙소 목록 조회**는 조건 없이 전체를 반환하는 정적 콘텐츠라 미리
받아 내부 매핑(`property`/`room_type`)으로 저장해 두고, **재고·요금 조회**는 검색 시점에 숙소 코드 목록을
넘겨 실시간으로 수행합니다. 이 성격 차이(자주 안 바뀜 vs 호출마다 바뀜)가 "매핑은 저장하고 요금·재고는
저장하지 않는다"는 설계의 근거입니다.

## 실패 판정 통일 — 어댑터가 공통 예외로

공급사 B는 장애 상황에서도 HTTP 200을 반환하고 본문의 `resultCode`로만 실패를 알립니다. 이를 확인하지
않으면 장애 응답을 정상 데이터로 처리하게 되므로, **어댑터가 실패를 하나의 공통 예외 타입으로 통일해
던집니다** — A의 4xx/5xx, B의 `resultCode ≠ "0000"`, 그리고 무응답(타임아웃)까지 전부 같은 예외로
수렴합니다. 덕분에 검색·오케스트레이션 계층은 실패가 어떤 모양으로 왔는지 모른 채, 공급사 무관 코드 한
벌로 부분 실패를 처리합니다.

실패의 **재시도 가능 여부(retryable) 분류도 어댑터의 책임**입니다. 일시적 실패(타임아웃, 5xx, 429, B의
`E500`/`E503`/`E429`)와 영구적 실패(4xx, `E400`/`E401`)의 구분은 각 공급사의 실패 체계를 아는 어댑터만
정확히 내릴 수 있습니다. 어댑터가 예외에 이 분류를 실어 보내면, 재시도를 도입하는 시점에 정책은 공급사를
몰라도 "retryable이면 재시도" 한 줄이 됩니다.

## 타임아웃 — 연결 1초 / 응답은 경로별 (검색 5초 · 동기화 10초)

연결과 응답의 역할을 분리해 각각 설정합니다. 값은 yml로 외부화해 환경별 오버라이드가 가능하며, 실측
지연 분포(p95/p99)가 쌓이면 그 근거로 조정합니다.

- **연결 1초** — 정상 연결은 수십 ms에 끝나므로, 통용 산식(RTT×3)보다도 여유 있는 1초를 넘긴다는 것 자체가
  인프라 장애의 신호입니다. 도달 불가 공급사를 빨리 판정해 실패시킵니다. 연결 수립은 경로와 무관해 하나만
  둡니다.
- **응답은 경로별로 다릅니다** — 검색은 고객이 기다리는 응답이고 동기화는 지연에 둔감한 배치라, 같은 값을
  쓸 이유가 없습니다.
  - **검색 5초** — 실제 공급사들의 응답 시간 분포를 모르는 현 시점의 의도적으로 관대한 출발값입니다. 짧게
    시작하면(2초 이하) 느리지만 정상인 응답을 일상적으로 잘라 부분 실패를 상시화하는 반면, 5초의 비용은
    장애 상황에서만 지불됩니다. 병렬 조회에서 전체 지연은 가장 느린 공급사가 결정하므로, 라이브러리
    기본값(무한 또는 10초)은 무응답 공급사가 검색 전체를 그만큼 묶게 해 채택하지 않았습니다.
  - **동기화 10초** — 숙소 목록은 payload가 크고(전체 목록) 사용자가 기다리지 않으므로, 느리지만 정상인
    응답을 잘라 동기화를 실패시키는 것보다 기다려 주는 쪽이 이득입니다. 구현은 WebClient 기본값을 짧은
    쪽(검색)으로 두고 동기화 경로가 요청 단위로 덮어씁니다 — 덮어쓰기를 잊어도 짧게 끊기는 쪽이 안전한
    기본값이기 때문입니다.

참고로 이 값들은 표준 조사를 거친 것입니다. 표준 숫자는 존재하지 않고, 라이브러리 기본값(OkHttp 연결·읽기
각 10초, Reactor Netty는 응답 타임아웃 기본값 없음)은 임의 대상용 보수값이며, 실무 원칙은 "연결은 RTT×3
수준, 응답은 호출자의 지연 예산에서 역산"입니다.

## 병렬 호출 — 청킹 50, 공급사별 동시성 8(bulkhead), e2e 데드라인 8초

재고·요금 API는 호출당 최대 50개 숙소 코드를 받으므로 코드를 50개씩 청크로 나눠 호출합니다(계약의 직접
귀결). 청크들은 병렬로 호출하되 동시성을 **공급사별로 격리**해 제한합니다 — 공급사마다 독립된 상한(기본 8)을
두어, 상한이 없을 때의 폭주(수천 개 규모에서 검색 1건이 수백 개 외부 호출을 발사해 429를 자극)를 막는
동시에, **전역 상한 하나였을 때 한 공급사가 슬롯을 독점해 다른 공급사를 굶기던 문제**를 없앱니다. 이 상한은
**`resilience4j.bulkhead` 설정이 단일 원천**입니다 — 검색 팬아웃이 그 값을 읽어 한 공급사 안에서만 상한까지
논블로킹으로 큐잉하고(Reactor `flatMap`), 같은 bulkhead 세마포어가 그 상한을 선언·계측합니다. 한 수를 두
곳(supplier 절과 bulkhead 절)에 나눠 두지 않아 드리프트가 원천적으로 없습니다.

### 정렬된 시스템 — 부등식으로 맞물린 값들

이 값들은 독립적이지 않고 서로 맞물립니다. 하나만 바꾸면 다른 값이 조용히 숨은 병목이 되므로,
`SupplierResilienceConfigTest` 가 아래 부등식을 고정합니다.

```
connect-timeout(1s)       <  search-response-timeout(5s)  <  search-deadline(8s)
bulkhead 동시성(8)          <  max-connections(16, 공급사별 풀)
pending-acquire-timeout(2s)  <  search-response-timeout(5s)
재시도는 남은 데드라인 안에서만 (데드라인이 재시도까지 취소)
```

- **e2e 데드라인(8초)**: 청크별 응답 타임아웃(5초)만으로는 느린 공급사가 검색 전체를 끌 수 있어, 검색
  전체에 상한을 둡니다. 데드라인 시점에 **도착한 결과는 유지**하고 미완 공급사는 `errors`에 `search
  deadline exceeded`로 채웁니다(부분 응답). 미완 청크는 취소되어 스레드·커넥션을 해제합니다. 도착분을
  버리는 `collectList().timeout()` 대신 `take(deadline)` 로 도착분을 보존합니다. 응답 타임아웃보다 커야
  최소 한 번의 시도가 끝날 여지가 있습니다.
- **커넥션 풀(공급사별, 상한 16)**: WebClient 풀을 공급사별로 분리해, 동시성 격리와 같은 원칙으로 한
  공급사의 커넥션 소진이 번지지 않게 합니다. bulkhead(8)보다 커야 전송 계층이 먼저 막히지 않고,
  pending-acquire 대기(2초)는 응답 타임아웃보다 짧아야 풀 고갈이 늦은 타임아웃으로 위장되지 않습니다.
- **재시도 정합**: e2e 데드라인이 재시도까지 포함해 총시간을 강제합니다 — 데드라인을 넘기는 재시도는
  취소되고 그 공급사는 TIMEOUT이 됩니다. 별도의 예산-인지 재시도(남은 시간이 부족하면 시도 자체를 스킵)는
  데드라인 취소가 이미 상한을 주므로 후속으로 둡니다.

MVC 블로킹 모델이라 e2e 데드라인이 곧 스레드 점유 상한 = 처리량 천장을 정합니다 — 이 정합을 맞추는 것은
견고성일 뿐 아니라 처리량 레버이기도 합니다. 값은 모두 출발값이며 실측(p95/p99) 후 조정합니다.

### 숙소 수천 개 규모의 대응 — 단계 로드맵

동시성 상한은 폭주를 막는 장치일 뿐 지연을 줄이지 못합니다. 청크 수 = 공급사 수 × ⌈N/50⌉이라 검색 지연이
N에 선형이고, 숙소 5,000개면 약 200청크 — 공급사별 8(공급사 2면 동시 16) 기준 13배치 순차로 6초대에
이릅니다(e2e 데드라인 8초를 넘기면 미완은 TIMEOUT). 대응은 비용이 싼 순서대로 단계화되어 있고, 각 단계는
지표가 발동을 판정합니다.

| 단계 | 발동 조건 | 수단 | 한계·비용 |
|---|---|---|---|
| 0 (현재 구현) | — | 청킹 50 + 공급사별 동시성 8(bulkhead) + e2e 데드라인 + 공급사별 커넥션 풀 + 지표 | 수천 개에서도 동작하되 지연이 N에 선형 |
| 1 | 검색 p95 초과 또는 429 관측(`rate_limited` outcome) | 공급사별 TTL 캐시 — 설계 확정 [CACHING.md](CACHING.md) | 인기 조합의 반복 조회만 제거 — **미스(첫 조회·비인기 조합)의 선형 지연은 그대로** |
| 2 | 캐시 히트율로도 p95 미달 | 백그라운드 사전 수집·스냅샷 — 검색이 스냅샷 조회가 되어 **지연이 N과 무관** | "요금·재고 저장 안 함" 원칙의 명시적 변경 + 신선도 체계(스냅샷 나이·갱신 주기) 동반. 공급사가 변경분(델타) 조회를 제공하면 수집 비용도 N 이 아닌 변경량에 비례하게 된다 |

검토 후 제외한 수단 — 조회 대상 축소(검색 계약이 "보유 숙소 전체"라 불가), 점진 응답(응답 계약 변경이
필요해 `/api/v2` 후보), 페이징(비범위).

## 부분 실패 허용

각 청크 호출의 실패는 개별로 흡수되어 전체 검색을 죽이지 않습니다. 성공한 공급사의 결과만으로 응답하고,
실패한 공급사와 사유는 응답의 `errors`에 드러납니다 — wire 표현과 HTTP 상태 의미론(전 공급사 실패도 200)은
[API.md](API.md)를 참고하세요.

## 재시도와 서킷 브레이커

Resilience4j(스택 결정, [TECH_STACK.md](TECH_STACK.md))로 구현되어 있습니다. 재시도는 두 원격 경로에
각각 다른 예산으로 적용됩니다 — 검색(재고·요금)은 고객이 기다리는 응답이라 **재시도 1회**, 동기화(숙소
목록)는 사용자 응답이 아닌 배치라 지연 여유가 있어 **재시도 3회**로 복구 확률을 높입니다. 검색 쪽은 원격
호출 Mono에만 입히므로 뒤따르는 정규화의 내부 예외는 재시도 대상도, 서킷의 실패 창에 기록될 일도
아닙니다.

- **무엇을 재시도하나**: `retryable`로 분류된 일시 실패 — 즉답형 오류의 **명시 집합**(500·502·503·504·
  429와 B의 미러 코드)과 무응답 **타임아웃 포함**. 기준은 "같은 요청을 다시 보내면 결과가 달라질 수
  있는가"입니다. 503·504는 약속된 일시성이라 자명하고, **500은 논의를 거친 판단**입니다 — 일시성의
  약속은 없지만 실무 500의 상당수는 인스턴스 단위 순단(재시작 중인 서버, 커넥션 순단)이라 재시도가
  청크(숙소 50개)를 살립니다. 결정적 500(특정 요청이 버그를 밟는 경우)이었을 때의 하방은 재시도 1회
  제한 + 서킷 차단으로 유계라 기대값이 양수입니다(주요 클라우드 SDK 들이 500을 기본 재시도 대상에 두는
  관행과 같은 판단). 501 같은 결정적 5xx 는 집합에서 제외됩니다. 반대로 502·504는 공급사 계약
  문서(400·401·429·500·503)에 없는 코드인데도 포함했습니다 — 공급사 앞단의 로드밸런서·게이트웨이가
  만들어내는 전송 경로의 현실이라, 계약에 없는 무응답 타임아웃을 처리하는 것과 같은 층위의
  판단입니다. 타임아웃 재시도는 최악의 경우 확인에
  쓴 5초를 한 번 더 지불하는 비용이 있지만, 일시 혼잡에서 회복할 기회를 버리지 않는 쪽을 택했습니다 —
  비용의 상한은 시도 횟수 제한과 서킷 브레이커가 만듭니다. 조회(GET)라 재시도가 안전하다는 멱등성이
  전제이며(숙소 목록 조회도 동일), 쓰기(예약)에는 별도 정책이 필요합니다. 판별은 어댑터가 붙인 분류를
  그대로 소비합니다(`RetryablePredicate`) — 무엇이 일시적 실패인지는 각 공급사의 실패 체계를 아는
  어댑터만 알기 때문입니다.
- **얼마나 기다리나**: 실패의 종류에 따라 갈립니다 — 한도 초과(429/`E429`)는 기본 1초(한도 창은 보통
  초 단위로 회복되므로 짧은 재시도는 한도를 더 두드릴 뿐), 그 외 일시 오류·타임아웃은 기본 200ms(순간
  혼잡의 회복을 노리는 짧은 간격). 기본 대기에는 **지수 백오프(×2, 대기 상한 5초)와 ±50% 지터**가
  붙습니다 — 백오프 곡선은 재시도 1회인 지금은 잠재적 장치지만 시도 횟수가 정책으로 바뀔 수 있고,
  지터는 동시 실패한 병렬 청크들이 정확히 같은 시각에 재발사되어 공급사를 다시 때리는 것을 막는 현재형
  장치입니다. `Retry-After` 헤더 존중은 검토 후 제외했습니다 — 이 공급사들은 해당 헤더를 주지 않아,
  쓰이지 않는 해석 경로를 유지하는 비용만 남기 때문입니다.
- **설정의 위치**: yml(`resilience4j.retry`)이 원천입니다 — 시도 횟수·인스턴스 선언은 값으로, 판별과
  대기 산정은 클래스 위임(`retry-exception-predicate`/`interval-bi-function`)으로 선언됩니다. 실패
  종류별 대기 차등은 스칼라 `wait-duration`으로 표현할 수 없어 규칙의 구현만
  코드(`SupplierRetryPolicy`)에 있습니다.
- **서킷 브레이커**: 공급사별 인스턴스로 분리해 반복 실패를 빠르게 차단합니다 — 관대한 타임아웃(5초)의
  반복 지불을 끊는 역할이고, 차단된 호출은 원격으로 나가지 않고 즉시 부분 실패(`errors[].reason:
  "circuit open"`)가 됩니다. 파라미터(yml `resilience4j.circuitbreaker`): 최근 10회 중 실패율 50% 이상이면
  open(청크 수가 적은 현 규모에서 장애가 검색 몇 건 안에 감지되도록 창을 작게), open 10초 뒤
  half-open으로 3회 시범 호출(일시 장애면 곧 복구 기회). **느린 호출도 창에 셉니다** — 검색 응답은 가장
  느린 청크에 끌려가므로, 타임아웃 미만이라도 2초를 넘는 호출이 최근 10회의 80% 이상이면 병든 연동으로
  보고 엽니다(실패 50%보다 문턱이 높은 이유: 느린 호출은 그래도 결과를 주므로 만성이라는 더 강한 증거를
  요구). 실패의 기록 범위는 해당 공급사 호출의 모든 예외입니다 — 영구 실패(401 등 설정 문제)의 반복도
  호출이 무의미하기는 마찬가지라, 서킷의 의미론을 "이 연동이 지금 동작하는가"로 잡았습니다. 값 조정은
  지표가 쌓인 뒤의 일입니다.
- **open 시의 대체 동작은 없습니다(검토 후 비채택으로 확정)**: 차단된 공급사는 부분 실패로 정직하게
  드러날 뿐, 마지막 성공 결과를 대신 서빙하는 fallback 은 두지 않습니다. 캐시 전략 논의에서 결론을
  내렸습니다 — 장애가 길어지면 캐시와 실제 재고의 괴리를 확인할 방법이 없어져, 보수 원칙과 충돌합니다.
  근거 상세는 [CACHING.md](CACHING.md)의 stale-if-error 절 참고.
- **적용 순서**: CircuitBreaker(안쪽) → Retry(바깥쪽). 재시도의 각 시도가 서킷의 실패 창에 기록되고,
  서킷이 열리면 재시도 판별이 차단 예외를 제외하므로 닫힌 문을 다시 두드리지 않습니다.

## 신규 공급사 추가 런북

경계가 지켜지고 있다면 아래 절차로 끝나며, 검색·동기화·정규화 계층은 수정할 필요가 없습니다.

1. `Supplier` enum에 새 공급사를 추가합니다 — 출처 표시와 내부 식별자의 네임스페이스가 여기서 생깁니다.
2. 어댑터 하나를 구현합니다. 책임은 정확히 세 가지입니다.
   - **숙소 목록 조회**: 원시 응답 → 표준 property/roomType 형태로 변환
   - **재고·요금 조회**: 요금 표현이 무엇이든 → 세금 포함 총액(gross)과 날짜별 잔여로 변환
   - **실패 통일**: 실패를 어떻게 알리든 → 공통 예외로 변환 + retryable 분류
3. base-url·인증 키·타임아웃을 yml에, 신규 공급사용 클라이언트 구성을 설정 계층에 추가합니다.
4. 어댑터 테스트를 추가합니다 — 파싱, 요금 변환, 실패 판정, 무응답 타임아웃.

**여기서 끝나야 합니다.** 기존 계층을 고쳐야 하는 상황이 생기면 그것은 어댑터 경계가 새고 있다는 신호이니,
추가를 진행하기 전에 설계를 먼저 의심하세요.
